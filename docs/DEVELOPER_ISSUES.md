# Заявки разработчикам из Confirmed

Статус: локальная генерация черновиков, одно-маркерных PoC и **ручной** выпуск
одного проверенного случая. Никакая публикация в GitHub или Svacer не происходит при генерации.
`verification.status=verified` само по себе не делает находку готовой заявкой.

## Локальная процедура

### Вкладка «Issue разработчику»

1. Откройте вкладку и выберите **«Текущая задача»** либо **«Все сохранённые задачи»**.
   Здесь показаны только сохранённые локальные решения `Confirmed`; состояние
   независимой проверки видно отдельно. Черновик Markdown доступен и до её окончания.
2. Выделите строки через Ctrl/Shift и нажмите **«Выбранные в очередь»** либо
   **«Все Confirmed в очередь»**. Поиск фильтрует список; кнопка «Все» берёт
   весь выбранный охват. Эта очередь отдельна от очереди анализа и Svacer-разметки.
3. Стандартный issue — короткий английский текст: заголовок `[TEAM]`,
   **Description** (компонент/commit, место, причина, достижимость, Source, Sink)
   и **Impact**. Текст анализа переводится и сокращается через Codex после
   согласия на передачу выбранных данных. Фрагменты кода в обычный issue не вставляются.
   При необходимости включите **«Также создать PoC через Codex»** до добавления.
   Для PoC согласие дополнительно охватывает связанные фрагменты исходников. PoC требует `verified`, точной
   ревизии и исходных доказательств. Код автоматически не выполняется.
4. Поле **«Одновременно»** задаёт 1–8 слотов подготовки issue/PoC и сохраняется
   между запусками. Это отдельная настройка от агентов анализа в «Настройках».
   Нажмите **«Подготовить очередь»**. Элементы обрабатываются в выбранном числе слотов;
   ошибка одного не мешает подготовке остальных. Остановка действует после
   сохранения уже запущенных элементов. Новые добавления во время запуска остаются
   в очереди до следующего запуска и нового согласия на передачу данных Codex.
   После аварийного закрытия выберите прерванный элемент
   и нажмите **«Повторить выбранные»**. Повтор сохраняет ручные изменения текста.
5. Выберите подготовленную строку в очереди. Заголовок и Markdown редактируются
   справа и автоматически сохраняются. Доступны просмотр, отдельное копирование
   заголовка/Markdown, экспорт `.md` и открытие папки issue/PoC. Это обеспечивает
   ручную передачу в GitHub, GitLab или внутреннюю систему без настройки токена.
   **«Вставить PoC в Markdown»** добавляет созданные файлы с отметкой «не запускался»;
   перед вставкой проверяются ревизия, решение и SHA-256 каждого файла.
   **«Кратко на английском…»** переписывает уже готовый черновик по сохранённому
   анализу в стандартном кратком формате. Прежний заголовок и текст сохраняются
   в подпапке `previous`; повтор очереди сам по себе ручные изменения не заменяет.
6. Кнопка **«Шаблон…»** позволяет менять язык, разделы и поля `$component`,
   `$revision`, `$description`, `$source`, `$sink` и другие. Изменения применяются
   к новым черновикам; существующий текст не перезаписывается. **«Вернуть стандартный»**
   восстанавливает краткие Description и Impact. CWE указывается только при
   достаточном обосновании; эффект и доступ не усиливаются при сокращении.

Очередь и черновики находятся в `RESULTS/developer-issues/`. Решения SAST и очередь
анализа не изменяются. Если ревизия или решение изменились после добавления,
подготовка блокируется: обновите список и добавьте актуальную строку заново.
Старый текст сохраняется в отдельном каталоге. Вкладка не публикует заявки;
консольная отправка ниже остаётся отдельной процедурой с собственным контрактом.

Markdown содержит краткое изложение сохранённого анализа. При переводе модели
передаётся только текст выбранного finding, без checkout и исходных фрагментов.
Перед передачей разработчику проверьте условия и влияние: генератор не придумывает
результаты запуска, CVSS или работающий патч. Настройки собственного шаблона могут
добавить подробные поля; стандартный шаблон их не включает.

PoC из карточки маркера и очередь issue работают в отдельных фоновых потоках:
можно анализировать другие маркеры, менять число агентов анализа, переключать
задачи, подключать новый проект и готовить материалы одновременно. Вверху окна
видны запущенные материалы с задачей/маркером; колонка **PoC** показывает процесс
или сохранённый результат. Один маркер не запускается повторно, пока его материалы
готовятся; очередь этого маркера ждёт, а другие элементы продолжают работу.
PoC, ранее созданный из карточки, подхватывается issue без нового запроса модели.
Удаление задачи и смена её исходников ждут сохранения её материалов; другие задачи
доступны. Если перепроверка изменит выбранное решение, прежние данные не принимаются
за результат новой версии: завершившаяся генерация сообщает об изменении решения.

### Сгенерировать PoC из карточки маркера

1. Выбрать в GUI один маркер со статусом `Confirmed` и завершённой независимой
   проверкой (`verification.status=verified`). В карточке нажать
   **«Сгенерировать PoC»** и подтвердить передачу данных Codex.
2. В запрос уходят данные выбранного решения и связанные с этим маркером
   фрагменты исходника из сохранённого контекста. Полный checkout не передаётся.
   Codex должен вернуть шаблонный `README.md` с идентификатором находки,
   ревизией, предусловиями, запуском, ожидаемым/фактическим результатом,
   контролем и ограничениями, а также исходник теста/harness в `poc/`.
   Если доказательств недостаточно, результат будет
   `needs_evidence` с конкретным списком недостающих сведений.
3. Файлы сохраняются в локальном хранилище задачи (обычно `RESULTS/generated-poc/`)
   с записью версии исходника,
   хешем решения, хешами файлов и точным запросом. Изменение версии или решения
   делает старый результат недействительным для карточки.
4. Генератор не запускает созданный код и помечает `reproduction_status` как
   `not_run`. Перед заявкой нужно самостоятельно проверить зависимость/сборку,
   выполнить PoC на точном baseline в изолированной среде, записать фактический
   эффект и сравнить его с отрицательным или исправленным контролем. Ошибка
   компиляции или отсутствие воспроизведения сами по себе не меняют вердикт.

1. Генерировать черновики только для Confirmed, чьи ID есть в сохранённой
   кампании. Другие маркеры и новые проекты не добавляются:

   ```powershell
   py app/developer_issues.py generate `
     --campaign RESULTS/analysis-campaign.json `
     --output RESULTS/developer-issue-drafts
   ```

2. Для каждого root cause вручную сверить, какие маркеры относятся к нему.
   Генератор пока создаёт *по одному черновику на маркер* и намеренно не
   утверждает, что это независимые ошибки. Объединить дубликаты до публикации.
   `poc-task.md` — автоматически составленное локальное задание на проверку,
   **не готовый PoC** и не подтверждение дефекта.
3. Проверить exact source revision, зависимости, сборку, все релевантные вызовы,
   защитные условия, штатный вход, права и реальный эффект. Исправить текст
   `body.md`: убрать заголовок `LOCAL DRAFT`, все `TODO` и недоказанные
   утверждения. Локальные Svacer URL, рабочие пути, секреты и внутренние
   идентификаторы не должны уходить во внешний отчёт.
4. Сгенерированный файл в локальном хранилище — кандидат на
   **настоящий** минимальный воспроизводитель, пока он не запущен и не проверен.
   Записать
   точную команду, ОС/архитектуру/флаги, результат baseline и контрольный
   результат на патче либо отрицательном сценарии. Содержимое текстового PoC
   до 32 КиБ должно быть включено в одобренный `body.md`: локальный путь к
   файлу разработчикам недоступен. Повторить тест. Если PoC
   не получается, не трактовать это автоматически как False Positive:
   сохранить пробел и не публиковать заявку как доказанную.
5. Подготовить минимальный patch и regression test либо честно отметить,
   что их пока нет. Patch не обязателен для API-отправки, но желателен для
   содержательной заявки разработчику. Проверить, что PoC и patch относятся
   к тому же commit, что и карточка.
6. Проверить `SECURITY.md`, разрешённый канал, существующие issue/advisory и
   целевой *upstream*, а не автоматически использовать внутренний mirror.
   Для security finding — приватный канал и согласованное раскрытие;
   публичная issue с PoC запрещена этим модулем. Для обычного бага допустима
   публичная issue после одобрения владельцем процесса. Перед отправкой сверить актуальную версию и правила целевого проекта.
7. Скопировать `review.template.v3.json` в `review.json`. Человек, который
   действительно провёл проверки, указывает целевой `owner/repo`, канал,
   `finding_kind`, имя проверяющего, заголовок, SHA-256 текущего `body.md` и
   PoC-файла, конкретные наблюдения и выставляет флаги проверок. Пустые поля
   или ложные флаги блокируют отправку. После любой правки текста/PoC хеши и
   одобрение надо обновить.
8. Только после отдельного решения пользователя и самостоятельного входа в
   GitHub CLI (`gh`) отправлять **одну** заявку. Команда `publish` требует
   точную фразу `PUBLISH <marker_id> TO <owner/repo> AS <channel>` и никогда
   не запускается генератором. Секреты в команду не передаются.

Перед отправкой выполнить локальный `check` с теми же `--campaign`, `--case`,
`--repo` и `--channel`. Он не делает сетевых запросов и перечисляет пробелы;
`publish_gate_passed` означает лишь выполнение формального контракта и
отмеченных человеком проверок, не гарантию отсутствия ошибок.
Этот gate повторно сверяет `source_evidence` с исходником через контекст,
назначенный именно данному marker ID, а не через последний `batch-context.json`.
`app/developer_issues.py publish --help` показывает параметры. При
сомнительном ответе сети остаётся `attempt.json`: перед повтором нужно
вручную сверить GitHub, чтобы не создать дубль. Успех фиксируется в
`receipt.json`. Наличие любого из этих файлов блокирует повторную отправку.

## Границы автоматизации

- Генератор может создать локальный исходник PoC для одного независимо
  проверенного Confirmed, но результат остаётся непроверенным до сборки и
  запуска. Он не создаёт патч, CVE, CVSS, доказательство эффекта или вывод о
  доступности атаки из одного SAST-комментария.
- Флаги в `review.json` — запись о человеческой проверке, не криптографическое
  доказательство. Статус `verified` сам по себе не разрешает публикацию.
- Для стороннего проекта API приватного отчёта доступен только если владелец
  включил private vulnerability reporting. В противном случае следовать
  security policy/контакту maintainer; не менять канал на открытую issue.
- Для API-публикации нужен установленный GitHub CLI с самостоятельным входом пользователя.

Официальные ориентиры: [GitHub private vulnerability reporting](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/report-privately),
[GitHub issue API](https://docs.github.com/en/rest/issues/issues),
[GitHub security advisory API](https://docs.github.com/en/rest/security-advisories/repository-advisories),
[GitHub CLI API](https://cli.github.com/manual/gh_api).
