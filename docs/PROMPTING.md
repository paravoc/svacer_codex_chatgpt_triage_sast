# Triage prompt contract

Prompt version: `2026-09-23.5`.

The active prompt is generated by `app/codex_run.py::build_runtime_prompt` for each
worker and verifier. `app/CODEX_TASK.md` describes the wider/manual workflow; a
background worker must not load it as a second instruction set. Saved prompts include
the version for later comparison. Historical prompts and completed results are not
rewritten when the generator changes.

## GPT-6 Sol tuning

The user-selected `gpt-6-sol` and existing `high` reasoning setting are preserved.
No model migration, API-authentication change or new tools are introduced.
Version `.2` also adds the bounded provider-error recovery described below.

The [OpenAI model guidance](https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices)
offers family-wide starting points for autonomy, instruction boundaries, writing,
delegation and proportional verification. It explicitly says the observations are
primarily about Astra and must be evaluated on the chosen model and workload.
The [Sol model page](https://developers.openai.com/api/docs/models/gpt-6-sol)
confirms the exact model identity. Reviewed 2026-09-23.

Application-specific adaptations:

- Background work proceeds without waiting for conversational approval. Missing facts
  produce source requests or explicit incomplete/challenged results, never guesses.
- Shared permissions and data/instruction boundaries precede source excerpts for both
  roles. Repository instructions, old verdicts and diagnostic text cannot authorize actions.
- The application owns parallelism: one assigned marker per primary worker, independent
  verification, no nested subagents or picking unrelated markers.
- Investigation ends when the scoped proof is complete. Repeating identical searches
  or inventing hypothetical integrations is not a completion requirement.
- A source request also saves the current incomplete result. Continuation retains facts;
  JSON/style repairs do not trigger a fresh investigation unless evidence changes.
- Visible progress reports new checked facts in Russian. The publication comment stays
  a short Russian paragraph with source references, without internal reasoning or jargon.

These rules do not weaken either verdict axis, exact-revision/excerpt validation,
mandatory independent verification of Confirmed, or explicit Svacer import approval.

## Validation and limits

Version `.5` makes publication comments self-contained for a reviewer: checked path,
decisive conditions/state changes, the supported conclusion and nearby source citations.
The usual length is 4-6 sentences, but a complete simple proof may be shorter; sentence
count is not a new validation gate. Multi-method or concurrency proofs explain the
relevant protections instead of merely asserting safety. Bounds/build/lifetime details
are included when decisive, not as boilerplate. Every claim still needs exact evidence;
extra prose never changes a verdict or demands speculative product integrations.
The active worker prompt and manual task instructions carry the same style-only example,
following the [official guidance on explicit instructions and examples](https://developers.openai.com/api/docs/guides/prompt-engineering).
The model, reasoning effort, validation, saved results and running sessions are unchanged.
Newly generated prompts use this version; an old runner must be restarted to load it.

Version `.4` explicitly requires both boolean verdict axes, including `false/false`
for False Positive. Validation names a missing or mistyped field separately from a
logical contradiction; it never invents or defaults the missing evidence. Publication
comments use formal Russian descriptions of the cause and proven consequence, not
colloquial failure wording. A recovered runtime error must not be described as process
termination. Code identifiers and evidence quotations remain unchanged.

Version `.2` gives primary workers the exact `Confirmed` severity/action enums and
includes validator feedback in every repair prompt, not only incomplete-review rounds.
Invalid values still fail validation; they are never silently mapped or defaulted.

Version `.3` states the verifier's string-array contract explicitly (unlike the
primary worker's object-based `source_evidence`). One verifier-local repair may use
the previous rejected answer and exact validator feedback. A second invalid answer
stays pending; the primary verdict and healthy peers are not rerun. This applies the
[official prompt-engineering guidance](https://developers.openai.com/api/docs/guides/prompt-engineering)
on explicit output requirements; it is not schema-constrained decoding or a promise
that a model cannot return an invalid answer.

Known model-capacity and transient service failures retry the affected worker at most
twice, after 5 and 15 seconds. Stop interrupts the wait. The same selected model,
cached sources and latest draft are retained; other workers continue independently.
Quota, authentication, unknown-model and malformed-output errors do not use this retry
path. Provider retries do not consume the source/evidence repair budget. If a failed
turn did not report usage, the aggregate usage is marked incomplete rather than exact.
An exhausted or non-transient failure is shown before older source gaps, while its
draft and evidence remain available for continuation. A provider outage can still
prevent completion; recovery does not manufacture a verdict or bypass proof checks.

Concurrent queue-state reads also retry brief Windows sharing/access-denied errors
within a bounded interval. Persistent failures and malformed JSON still raise an
error; they must never be interpreted as an empty queue.

Offline tests exercise prompt generation, primary/verifier output contracts, model
selection, privacy constraints, source continuation, evidence validation and result
transport. They do not demonstrate improved model accuracy, speed or token cost.

Before claiming a quality improvement, compare old and new prompts on the same small,
explicitly authorized set of pinned markers (at most five for the initial trial).
Include a guarded false positive, a reachable defect, a proven component-only defect,
a missing-source continuation and a recheck with a misleading old comment. Keep model,
reasoning effort and source inputs fixed; do not upload results automatically.

Record evidence correctness, supported verdict, accepted JSON, comment readability,
remaining gaps, elapsed time and actual token usage. Repeated trials are needed to
separate prompt effects from model variability. No such live comparison was run as
part of this prompt-only update.
